# Глава 11. FAQ и грабли

## Зачем эта глава

Это сборник вопросов, которые возникали по ходу работы, и проблем, на которые мы наступали. Часть — про сам код расширения, часть — про Chrome и MV3, часть — про конвертер и правила.

Если что-то не работает или непонятно — сначала сюда. Если ответа нет — перечитать соответствующую главу.

## Часть 1. Разработка и отладка

### Расширение загрузилось, но ничего не работает

Три места, где искать ошибки, по порядку.

**1. Страница `chrome://extensions`.** В карточке расширения бывает блок Errors. Если он есть — это ошибки манифеста или парсинга файлов. Читаем, исправляем.

**2. Console service worker'а.** Открывается так: `chrome://extensions` → карточка нашего расширения → ссылка Service worker. Там логи `[erst_dev_adblocker] service worker started` и все ошибки из модулей `background/lib/`.

Если строки `service worker started` нет — значит, `service_worker.js` не выполнился вообще. Причина либо в синтаксисе, либо в манифесте (неверный путь или опечатка в имени).

**3. Console страницы.** F12 на любом сайте → Console. Там логи content scripts `[erst-dev] refreshed for ...` и ошибки из модулей `content/lib/`.

### Popup открывается пустой

Чаще всего причина — в popup.js не работает импорт.

Проверить в `popup.html`:

```html
<script type="module" src="popup.js"></script>
```

Если забыть `type="module"` — Chrome выдаст ошибку `Cannot use import statement outside a module`. Popup появится, но пустой — HTML отрисовался, JS упал до первого рендера.

Второе место — Console popup. Открыть правой кнопкой по popup → Inspect. Там будет видно.

### Изменения в коде не подхватываются

Chrome кэширует расширение. Изменения файлов **не применяются** автоматически.

После каждой правки — идти на `chrome://extensions` и нажимать значок перезагрузки ⟳ на карточке расширения.

Отдельно про service worker: если он уже был запущен, старая версия продолжит работать даже после перезагрузки расширения. Останавливается только при явной перезагрузке или засыпании. Иногда полезно закрыть окно Console service worker'а и открыть заново.

### В Console service worker'а старая версия кода

Та же причина. Chrome не перезагружает worker при каждой правке. Нужно нажать ⟳ на карточке расширения — там же, где обычно.

Если совсем странно себя ведёт — полностью удалить расширение и загрузить заново через Load unpacked.

### Ошибка «Could not load manifest»

Манифест невалиден. Три частых причины.

Первая — лишняя запятая в JSON. JSON не допускает запятую после последнего элемента. Проверяем в редакторе — WebStorm подсвечивает.

Вторая — неверный путь к файлу. `service_worker.js` вместо `background/service_worker.js`. Проверяем каждую строку в блоке `background`.

Третья — неправильные права. Если в `permissions` опечатка (`declarativeNetRequest` через `r` в середине), Chrome ругнётся.

### Ошибка «Rule with id N does not have a unique ID»

См. часть 3 — про диапазоны id.

### Ошибка «This request exceeds the MAX_GETMATCHEDRULES_CALLS_PER_INTERVAL quota»

Мы с этой ошибкой сталкивались, когда игрались со счётчиком заблокированных правил через `getMatchedRules`. Chrome ограничивает количество вызовов этого API до 20 в минуту.

Решение — не вызывать `getMatchedRules` при каждом открытии popup. Либо кэшировать результат, либо использовать другой подход. У нас счётчика нет — статус показывается только в popup.

## Часть 2. MV3-специфика

### Почему service worker засыпает и почему это важно

В MV2 фон был постоянной HTML-страницей. В MV3 Google заменил его на service worker для экономии памяти. Service worker живёт только пока есть события. Через 30 секунд без событий Chrome его усыпляет.

**Что это значит для кода:**

- Переменные модуля обнуляются при каждом засыпании. Нельзя хранить состояние в `let someVar`.
- Состояние — только в `chrome.storage`.
- `addListener` регистрируется синхронно на верхнем уровне файла, а не внутри асинхронных операций. Иначе Chrome может усыпить worker до регистрации, и событие потеряется.
- `console.log` в начале файла выполняется **при каждом** пробуждении, не только при загрузке расширения.

Подробно — глава 4.

### Почему нельзя использовать webRequest

`chrome.webRequest` в MV3 доступен только для **наблюдения**, не для блокировки. Раньше в MV2 можно было перехватывать запросы и решать «блокировать или нет». Теперь это запрещено — вместо этого DNR.

Технически `webRequest` в MV3 всё ещё есть, но блокирующая часть вырезана. Осталось только смотреть, без вмешательства.

Причина запрета — безопасность и производительность. Chrome не хочет, чтобы расширение тормозило загрузку страниц, пока думает над каждым запросом.

### Почему content script не может import

Content scripts — не модули. Chrome выполняет их как обычные `<script>`-теги: файлы загружаются последовательно, в общем контексте, без поддержки `import` и `export`.

Причина — историческая. Content scripts появились до ES-модулей. Сейчас их не переводят, потому что это сломало бы тысячи существующих расширений.

Как обошли — разбили на семь файлов и подключили массивом в манифесте. Подробно — глава 5.

### Что делать с SPA-сайтами

SPA меняет содержимое страницы без перезагрузки. Событие `webNavigation.onCommitted` при этом **не срабатывает** — оно реагирует только на настоящие переходы.

Решение — перехватывать `history.pushState`, `history.replaceState` и слушать `popstate` и `hashchange`. Плюс периодическая проверка URL раз в секунду — страховка от экзотических фреймворков.

Реализация — `content/lib/spa.js`. Подробно — глава 5.

### Service worker не может загрузить файл через fetch

По умолчанию Chrome запрещает расширению читать свои файлы через `fetch`. Нужно явно разрешить в `manifest.json`:

```json
"web_accessible_resources": [
  {
    "resources": ["rules/cosmetic-map.json"],
    "matches": ["<all_urls>"]
  }
]
```

Только файлы из списка `resources` можно читать. У нас там только `cosmetic-map.json`. DNR-файлы читает Chrome сам, им этот блок не нужен.

### Требуется «return true» в onMessage

Если внутри обработчика `chrome.runtime.onMessage` есть `await` перед `sendResponse`, нужно вернуть `true` из обработчика. Без этого Chrome закроет канал до того, как `sendResponse` долетит. Popup получит ошибку «message port closed».

Подробно — глава 2, раздел «Что такое `return true`».

## Часть 3. Диапазоны id — самая частая проблема

### Почему «Rule with id 1 does not have a unique ID» на пустом месте

Мы эту ошибку ловили несколько раз, пока разбирались. Причины было три разных.

**Первая — динамические правила конфликтуют со статическими.** Chrome использует единое пространство id для статических и динамических DNR-правил. Если в `ads.json` есть правило с id=1, динамическое правило с id=1 создать нельзя.

Решение — разделить диапазоны. Статические правила — 10 000+, исключения — 100 000+, динамические — 1..9999. Подробно — глава 8.

**Вторая — удаление и добавление в одном вызове.** Если в одном `updateDynamicRules` вызвать `removeRuleIds: [1,2,3]` и `addRules: [{id:1, ...}]`, Chrome может применить добавление раньше удаления — и увидеть конфликт id=1.

Решение — разделить на два вызова. Сначала удалить, дождаться, потом добавить.

**Третья — race condition.** Два вызова `syncDnrState` параллельно создают правила с одинаковыми id. Первый создал, второй пытается создать то же самое — конфликт.

Решение — мьютекс `syncInFlight` в `syncDnrState` и единственный источник вызовов (только `storage.onChanged`). Подробно — глава 9.

### Сколько всего правил можно загрузить

- Статические DNR — 30 000 суммарно.
- Динамические DNR — 5 000.
- Сессионные DNR — 5 000.

Суммарно 40 000, но лимиты не складываются автоматически. Статические — жёсткий потолок 30 000 на всё расширение, включая все ruleset'ы.

У нас: 28 024 блокирующих + 501 allow + ~50 manual = 28 525 статических. Плюс до 5 000 динамических для whitelist.

## Часть 4. Конвертер и правила

### Почему в rules/ads.json так мало правил — у нас же 50 000 из EasyList

Потому что Chrome не принимает больше 30 000 статических правил. Из ~100 000 потенциальных мы оставляем 28 500 по квотам.

Квоты: этап 2 (с `$`) — все 4 500, этап 3 (path) — 15 000, этап 1 (`||domain^`) — 8 500, исключения — 500.

Остальное режется. Какие именно правила теряются: 41 500 простых `||domain^` из 50 000 и 39 000 path-правил из 54 000.

Почему не больно: EasyList отсортирован по популярности. Топовые рекламные домены в начале, редкие в конце. Мы оставляем начало — самые нужные правила.

Подробно — глава 8.

### Почему некоторые правила с EasyList не конвертируются

Модификаторы `$domain=`, `$replace`, `$csp`, `$removeparam`, `$popup`, `$document` и другие DNR не поддерживает. Правила с ними пропускаются целиком.

Процент пропущенных небольшой — из 8 745 правил с `$` пропущено 4 220. Из 50 000 простых — 0. Из 54 000 path — 12 (не-ASCII символы).

### Что делать, если нужно добавить своё правило

Два места для ручных правок.

**Правило блокировки сети** — в `rules/manual.json`. Дописать объект в JSON-массив. Формат как у обычных DNR-правил, диапазон id 1..100.

**Косметический селектор** — в `content/cosmetic-manual.css`. Просто CSS с `display: none !important`.

Эти файлы **не перезаписываются** конвертером. Можно спокойно править, следующий запуск `node tools/convert.js` их не тронет.

### Почему конвертер не пишет в manual.json

Он для этого не предназначен. `manual.json` — источник ручных правил, которые конвертер не генерирует. Он даже не читает этот файл. Если бы конвертер писал туда — затирал бы правки.

### Как обновить правила из свежих EasyList

1. Скачать свежие `easylist.txt` и `adguard-russian.txt` в `lists/`.
2. Запустить `node tools/convert.js`.
3. Перезагрузить расширение (⟳ на карточке).

Всё. Файлы `rules/ads.json`, `rules/exceptions.json`, `content/cosmetic.css`, `rules/cosmetic-map.json` перезапишутся.

`rules/manual.json` и `content/cosmetic-manual.css` — не тронутся.

## Часть 5. Отдельные сайты

### Mail.ru — почему нативная реклама не скрывается

Mail.ru использует шифрование текста метки. Слово «Реклама» разбито на куски по буквам, они подгружаются в разных элементах: «P», «екл», «keP», «ama». Наш поиск по прямому тексту (в `ad-markers.js`) не срабатывает.

Это известное ограничение метода поиска по тексту. AdBlock и uBlock тоже с этим мучаются. Полностью победить сложно — Mail.ru специально усложняет жизнь блокировщикам.

Что у нас работает: полноэкранные баннеры (`[isfullscreen="true"]`), рекламные блоки через `data-mnemo` в виджетах, сайдбар с РСЯ. Нативная реклама в ленте — остаётся.

### Яндекс.Погода — реклама в видеорекламе в сайдбаре

Используется shadow DOM. Внутри `<div id="money-main-*">` создан изолированный DOM с классом `AppMoney_container`. Обычный CSS туда не проникает.

Решение — скрыть сам внешний контейнер `<div id="money-main-*">`. Через CSS это работает: селектор `[id^="money-main-"]` находит элемент, и он скрывается со всем содержимым.

Подробно — `content/cosmetic-manual.css`.

### Dzen — откуда взялся `data-testid*="-ad"`

Dzen использует семантические атрибуты `data-testid` для своих тестов. Один из них — `main-one-column-right-ad` для рекламных блоков. Мы это нашли и используем через селектор `[data-testid$="-ad"]`.

Работает надёжно — эти атрибуты меняются реже, чем CSS-классы. Dzen сам «помечает» свою рекламу.

### ВК — почему видео не блокируется, а пропускается

Пре-роллы в ВК (и YouTube, и RuTube) склеены с основным видео на сервере. В сетевом запросе это **один** поток. Разрезать нельзя — DNR не умеет обрабатывать фрагменты потока.

Единственный рабочий способ — нажать кнопку «Пропустить». Мы это делаем автоматически через интервал раз в секунду в `auto-skip.js`. Реклама мигает на долю секунды и пропадает.

## Часть 6. Идеи и обсуждения

### Разделить DNR-набор на core и extra

Сейчас мы режем ~100 000 правил до 28 500 из-за лимита Chrome. Идея: сделать два набора.

**Core** — 28 000 самых популярных правил, включён всегда. То, что у нас сейчас.

**Extra** — второй набор (тоже ~28 000), который пользователь включает опционально вместо core. Не вместе, а переключением — потому что лимит 30 000 общий.

Смысл: разные пользователи хотят разное. Один хочет то, что режет все популярные рекламные сети. Другой хочет максимум покрытия для редких сайтов. Тумблер в popup — «Core / Extra».

Реализация: два набора правил, в `updateEnabledRulesets` включается один или другой. В popup — переключатель.

Пункт обсуждения на после-MVP.

### Тесты

Обсуждали, решили не делать. Личный проект, выхлопа мало. Проверяем руками.

### TypeScript, Prettier, ESLint

Планируется после MVP. Сейчас пишем на чистом JS. TypeScript добавил бы типы для сообщений, объектов state, DNR-правил. Prettier — единый формат. ESLint — ловля типичных ошибок.

Причины отложить: пока проект в активной разработке, TS мешает каждым изменением типов. После релиза — стабильное состояние, можно спокойно переводить.

### Порт на Firefox

Планируется после MVP. Firefox поддерживает MV3, но есть нюансы:

- `browser.*` вместо `chrome.*` (хотя `chrome.*` тоже работает через алиас).
- Лимиты DNR больше 30 000.
- Поддерживает блокирующий `webRequest` даже в MV3 — можно использовать более мощный API.

Потребуется отдельный `manifest.firefox.json` и тесты на реальном Firefox. Основной код должен работать без изменений.
