# Глава 9. Whitelist и вкл/выкл — управление состоянием

## Зачем эта глава

В расширении есть два независимых переключателя:

1. Вкл/выкл расширения целиком — глобальный тумблер в popup.
2. Белый список сайтов — на каких сайтах блокировка отключена.

Оба влияют на три уровня сразу: включены ли DNR-ruleset'ы, работают ли domain-specific селекторы, ставится ли косметический CSS на страницы. Всё это должно быть синхронно.

Синхронность — самая сложная часть MV3. Между popup, service worker и storage происходит несколько асинхронных операций, и если их неправильно упорядочить — возникают race conditions с непонятными ошибками.

В этой главе разберём:
- Что такое whitelist и зачем он нужен.
- Как работают вкл/выкл и whitelist на всех трёх уровнях.
- Что такое race condition и как мы его поймали.
- Почему `syncDnrState` вызывается только через `storage.onChanged`, а не напрямую.
- Зачем мьютекс в `syncDnrState`.

## Что такое whitelist

Whitelist (белый список) — это список доменов, на которых блокировка не работает. Пользователь сам решает, какие сайты туда добавить.

Типичные причины:

- Сайт ломается из-за слишком агрессивных правил — кнопки не нажимаются, формы не отправляются.
- Пользователь хочет поддержать сайт — блокировщик выключается, реклама показывается, сайт зарабатывает.
- Сайт сам по себе без рекламы, но что-то в блокировщике срабатывает по ошибке.

Пользователь добавляет домен через popup одной кнопкой. Дальше блокировка на этом сайте не работает — пока пользователь не удалит домен из списка.

## Как whitelist работает на трёх уровнях

Whitelisted сайт должен быть полностью исключён из блокировки. Это значит три уровня:

**1. DNR-правила.** Все блокирующие правила для этого сайта должны быть отключены. Иначе Chrome продолжит резать сетевые запросы.

**2. Общий CSS.** Косметические правила в `cosmetic.css` не должны вставляться на эту страницу. Иначе скрытые элементы останутся скрытыми.

**3. Domain-specific CSS.** Селекторы из `cosmetic-map.json` для этого домена тоже не должны применяться.

Все три уровня работают независимо. Их надо синхронизировать — если обновить только один, получится рассогласование (например, CSS не вставляется, а DNR продолжает блокировать).

## Три уровня — как каждый управляется

### DNR — динамические правила allowAllRequests

Для каждого whitelisted домена создаётся динамическое DNR-правило с действием `allowAllRequests`. Это специальное действие Chrome: «разреши все запросы, инициированные этой страницей».

Почему не просто `allow`: `allow` разрешает конкретный запрос. `allowAllRequests` разрешает всё внутри страницы, включая запросы на чужие домены (рекламные CDN, трекеры и т.д.). Для whitelist нужен именно второй.

Правило выглядит так:

```json
{
  "id": 1,
  "priority": 100,
  "action": { "type": "allowAllRequests" },
  "condition": {
    "urlFilter": "||rbc.ru^",
    "resourceTypes": ["main_frame", "sub_frame"]
  }
}
```

`priority: 100` — выше блокирующих (у них 1) и обычных allow (у них 2). Если пользователь добавил `rbc.ru` в whitelist, все запросы с этого сайта разрешены, что бы ни говорили другие правила.

`resourceTypes: ["main_frame", "sub_frame"]` — `allowAllRequests` работает только для запросов, создающих страницу. Это его требование: он действует на «всю страницу», а не на отдельный запрос, поэтому привязывается к созданию страницы.

Создание и удаление этих правил — в `shared/storage.js`, функция `syncWhitelistRules` (разбирали в главе 7).

### Общий CSS — проверка в service worker

Общий CSS вставляется в `background/lib/cosmetic-injector.js`, в функции `handleCommitted`. Перед вставкой — проверка:

```js
if (!enabled) return;
const whitelisted = await isWhitelisted(details.url);
if (whitelisted) return;
```

Если сайт в whitelist — `insertCSS` не вызывается вообще. Тег `<style>` в страницу не попадает.

### Domain-specific CSS — проверка в message-handler

Content script запрашивает domain-specific селекторы у service worker'а. Тот отвечает через `handleGetDomainSelectors`:

```js
const enabled = await getEnabled();
if (!enabled) { sendResponse({ selectors: [] }); return; }

const whitelisted = await isWhitelisted(msg.url);
if (whitelisted) { sendResponse({ selectors: [] }); return; }
```

Если сайт в whitelist — service worker отвечает пустым массивом. Content script ничего не вставляет.

Все три уровня проверяют состояние независимо. Это важно: даже если один уровень по каким-то причинам не обновился, остальные работают корректно.

## Глобальный вкл/выкл

Это второй переключатель. Работает так же, как whitelist, но на всех сайтах сразу.

Когда пользователь выключает расширение:

- Все DNR-ruleset'ы выключаются через `updateEnabledRulesets`.
- Динамические whitelist-правила удаляются (незачем держать, всё равно выключено).
- Общий CSS больше не вставляется — проверка `if (!enabled) return` в `handleCommitted`.
- Domain-specific селекторы не отдаются — проверка в `handleGetDomainSelectors`.

Когда включает обратно — всё возвращается.

Разница с whitelist: whitelist — это про конкретные сайты, вкл/выкл — про всё расширение. Пользователь может выключить расширение и не заходить в интернет вообще, либо добавить один сайт в whitelist и там спокойно смотреть рекламу.

## Хранение состояния

Оба переключателя живут в `chrome.storage.local`:

```js
{
  "enabled": true,
  "whitelist": ["rbc.ru", "habr.com"]
}
```

`enabled` — булево. `whitelist` — массив строк.

В service worker эти значения не хранятся в переменных. Причина — в главе 4: service worker засыпает, переменные обнуляются. Каждый раз читаем из storage.

Чтение и запись — через `shared/storage.js`:
- `getEnabled()` / `setEnabled(value)`.
- `getWhitelist()` / `addToWhitelist(domain)` / `removeFromWhitelist(domain)`.

Проверка «в whitelisted ли сайт» — функция `isWhitelisted(url)`. Она разбирает hostname, идёт по всем родительским доменам и проверяет, есть ли хоть один в списке. Подробно — глава 7.

## Race condition — главная проблема

А теперь самое важное в этой главе.

Race condition (состояние гонки) — это когда два процесса выполняются параллельно, но зависят друг от друга, и результат зависит от того, кто первым успел.

В нашем расширении это проявляется так: два вызова `syncDnrState` запускаются почти одновременно.

Как это происходит:

1. Пользователь открывает popup, добавляет `news.mail.ru` в whitelist.
2. Popup отправляет service worker'у сообщение `popup→sw:whitelistAdd`.
3. Service worker получает сообщение, вызывает `addToWhitelist(domain)` — это пишет в `chrome.storage.local`.
4. Chrome тут же триггерит событие `chrome.storage.onChanged` для нашего service worker'а — «поле `whitelist` изменилось».
5. Слушатель `storage.onChanged` (в `service_worker.js`) вызывает `syncDnrState()`.
6. Параллельно сам handler сообщения тоже вызывает `syncDnrState()`.

Два вызова `syncDnrState` идут параллельно. Каждый:

1. Читает `enabled` и `whitelist` из storage.
2. Читает текущие динамические правила Chrome.
3. Удаляет старые правила.
4. Создаёт новые по списку из storage.

И тут начинается беда. Оба вызова одновременно видят старое состояние (одно и то же). Оба удаляют одни и те же старые правила. Оба пытаются создать новые правила с одинаковыми id. Второй вызов получает ошибку:

```
Error: Rule with id 1 does not have a unique ID.
```

Именно эту ошибку мы ловили, когда только начали работать с whitelist. Она сбивала с толку: правило мы только что удалили, почему Chrome говорит, что id занят? Ответ — потому что второй вызов уже успел создать новое правило с тем же id, пока первый вызов ещё думал.

Дополнительный нюанс: `chrome.storage.onChanged` срабатывает асинхронно. То есть если handler сообщения сделает `await addToWhitelist(domain)`, потом `await syncDnrState()`, а событие storage прилетит между этими двумя await — получим ещё более неприятный сценарий, где оба вызова идут почти одновременно.

## Как мы решили race condition

Два изменения в коде.

### Первое: убрать прямые вызовы syncDnrState из handlers

Раньше `handleWhitelistAdd` в `message-handler.js` выглядел так:

```js
async function handleWhitelistAdd(msg, sendResponse) {
  const list = await addToWhitelist(msg.domain);
  await syncDnrState();  // ← лишний вызов
  sendResponse({ ok: true, whitelist: list });
}
```

Мы убрали `await syncDnrState()`. Теперь:

```js
async function handleWhitelistAdd(msg, sendResponse) {
  const list = await addToWhitelist(msg.domain);
  // syncDnrState НЕ вызываем — его триггерит chrome.storage.onChanged
  sendResponse({ ok: true, whitelist: list });
}
```

Логика простая: handler пишет в storage, а синхронизацию DNR делает только слушатель `storage.onChanged`. Один источник правды для синхронизации. Никаких параллельных вызовов.

То же самое для `handleSetEnabled` и `handleWhitelistRemove` — убрали прямые вызовы `syncDnrState`.

### Второе: мьютекс в syncDnrState

Даже с одним источником вызовов остаётся возможность параллельного запуска. Например, пользователь быстро кликает по свитчеру дважды, или `storage.onChanged` приходит дважды подряд с разными полями.

Мы добавили мьютекс — защиту от параллельных запусков:

```js
let syncInFlight = null;

export async function syncDnrState() {
  if (syncInFlight) {
    return syncInFlight;
  }

  syncInFlight = (async () => {
    try {
      // ... логика ...
    } finally {
      syncInFlight = null;
    }
  })();

  return syncInFlight;
}
```

Как это работает:

- Если `syncInFlight === null` — мы первые. Запускаем работу, сохраняем промис в `syncInFlight`.
- Если `syncInFlight !== null` — кто-то уже запустил синхронизацию. Возвращаем его промис, не запуская второй работы.
- В `finally` — обнуляем `syncInFlight`, чтобы следующий вызов мог запуститься.

Гарантия: в любой момент времени работает не более одной `syncDnrState`. Все параллельные вызовы ждут завершения первой.

`finally` важен: если внутри логики что-то упадёт с ошибкой, блок `finally` всё равно выполнится и сбросит флаг. Без него после первой ошибки синхронизация больше никогда не запустилась бы — `syncInFlight` остался бы заполненным навсегда.

## Дополнительная защита: разделение удаления и добавления

В `syncWhitelistRules` мы уже давно разделили удаление старых и добавление новых правил на два разных вызова `updateDynamicRules`:

```js
// Удаляем старые
if (existingIds.length > 0) {
  await chrome.declarativeNetRequest.updateDynamicRules({
    removeRuleIds: existingIds
  });
}

// ... потом добавляем новые
if (newRules.length > 0) {
  await chrome.declarativeNetRequest.updateDynamicRules({
    addRules: newRules
  });
}
```

Причина: Chrome не гарантирует порядок обработки `removeRuleIds` и `addRules` в одном вызове. Бывает так, что Chrome сначала добавляет новые правила, потом удаляет старые — и в момент добавления получает конфликт id (новое правило с id=1 и старое с id=1 одновременно). Отсюда та же ошибка «unique ID».

Разделение на два вызова гарантирует: удаление применилось, только потом добавление.

## Полная цепочка при добавлении сайта в whitelist

Соберём всё вместе. Пользователь добавляет `news.mail.ru`:

1. Popup: клик по кнопке «Добавить news.mail.ru».
2. Popup отправляет service worker'у сообщение `popup→sw:whitelistAdd` с доменом.
3. Service worker: `handleWhitelistAdd` вызывает `addToWhitelist("news.mail.ru")`.
4. `addToWhitelist` читает текущий whitelist из storage, добавляет домен, пишет обратно в storage.
5. Chrome триггерит `chrome.storage.onChanged` — «поле whitelist изменилось».
6. `syncDnrState` вызывается только через слушатель storage (не через handler).
7. `syncDnrState`:
   - Проверяет мьютекс — синхронизация не идёт, запускаем.
   - Читает `enabled` из storage — `true`.
   - Вызывает `setRulesetsEnabled(true)` — ruleset'ы уже включены, ничего не меняем.
   - Вызывает `syncWhitelistRules(true)`:
      - Читает существующие динамические правила.
      - Удаляет старые через `removeRuleIds`.
      - Создаёт новое правило для `news.mail.ru` через `addRules`.
   - Логирует результат.
8. Service worker: `handleWhitelistAdd` отвечает popup'у с обновлённым списком.
9. Popup: получает ответ, перерисовывает список.

Теперь если пользователь обновит страницу `news.mail.ru` (F5):

1. `chrome.webNavigation.onCommitted` срабатывает для главного фрейма.
2. `handleCommitted` в `cosmetic-injector.js` проверяет `isWhitelisted("https://news.mail.ru/...")`.
3. Функция возвращает `true` — домен в whitelist.
4. CSS не вставляется.
5. Content script запрашивает селекторы у service worker'а.
6. Service worker проверяет `isWhitelisted` — `true`. Отвечает пустым массивом.
7. Content script ничего не вставляет.
8. DNR — Chrome применяет динамическое правило `allowAllRequests` для `news.mail.ru`, которое разрешает все запросы с этого сайта.
9. Реклама на `news.mail.ru` появляется.

Все три уровня согласованы. Работает.

## Почему нельзя просто перезапустить расширение

Соблазн: при каждом изменении whitelist перезагружать расширение целиком. Тогда все динамические правила создаются заново, storage читается заново, всё в консистентном состоянии.

Проблемы:

- Перезагрузка расширения убивает все вкладки пользователя. Нельзя делать это в рантайме.
- `chrome.runtime.reload()` недоступен из service worker'а (только из popup, и то нежелательно).
- Даже если бы можно было — пользователь ждал бы секунду каждый раз при добавлении домена. Плохой UX.

Поэтому правим состояние инкрементально — тем, что описано выше.

## Что могло бы пойти не так

**Ошибка `syncWhitelistRules` в середине работы.** Например, удаление старых правил прошло, а добавление упало. Состояние: старых правил нет, новых тоже нет. Chrome не блокирует `news.mail.ru` (потому что нет блокирующих правил для него) — и не разрешает специально (потому что нет `allowAllRequests`). То есть работает как обычный сайт, к которому применимы блокирующие правила. Слегка некорректно, но не критично. При следующем изменении whitelist всё пересоздастся.

**Storage переполнен.** `chrome.storage.local` имеет лимит 5 МБ. Наши данные — два поля, весят копейки. Никогда не переполнится.

**Пользователь добавил 10 000 сайтов в whitelist.** Лимит динамических правил — 5 000. После 5 000-го сайта `syncWhitelistRules` начнёт пропускать домены с предупреждением `[DNR] whitelist too large, skipping`. На практике никому не нужно 5 000 сайтов в белом списке, но защита есть.

**Service worker уснул между записью storage и обработкой `storage.onChanged`.** Это невозможно: Chrome не усыпляет service worker, пока есть незавершённые события. Событие `storage.onChanged` гарантированно доставляется до засыпания. Даже если бы усыпил — при следующем пробуждении событие бы доставилось (Chrome ставит его в очередь).
