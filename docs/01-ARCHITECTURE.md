# Глава 2. Архитектура

## Зачем эта глава

Расширение — это не один файл, а **набор файлов**, которые работают в **разных местах браузера**. Они не видят друг друга напрямую. Они общаются через сообщения. Они решают разные задачи.

Если сразу не понять эту архитектуру — дальше будет каша. Каждая строчка кода будет казаться случайной.

В этой главе разберём:
- Какие вообще бывают «миры» в расширении.
- Что делает каждый мир.
- Как миры общаются.
- Как выглядит наш проект целиком.
- Как проходит **полный цикл** — от запуска браузера до блокировки конкретной рекламы.

## Три «мира» расширения

В MV3 есть **три независимых контекста**, в которых выполняется код расширения. Они **изолированы друг от друга** — не видят переменные друг друга, не могут вызывать функции друг друга. Общаются **только через сообщения**.

Три мира:

1. **Service worker** — «мозг», работает в фоне.
2. **Content script** — «руки», работает на каждой открытой странице.
3. **Popup** — «лицо», показывается, когда пользователь кликает на иконку.

Плюс есть **четвёртый мир**, но он не расширения, а браузера:
4. **Страница сайта** — сам сайт, который ты открыл. Наш content script живёт **рядом** с ним, но **не внутри** (изолированная среда).

### Аналогия — ресторан

Представь, что расширение — это **ресторан**:
- **Повар на кухне** = service worker. Готовит, знает рецепты, но его не видно из зала. Работает **в фоне**, может спать между заказами.
- **Официант в зале** = content script. Работает **на конкретном столике** (на конкретной странице). Общается с гостем (сайтом), передаёт заказы на кухню.
- **Вывеска и меню на входе** = popup. Видно только когда заглядываешь. Показывает состояние, позволяет заказать.

Официант **не готовит**, повар **не общается с гостями**. Они передают записки через кассу (сообщения).

⚠️ **Аналогия не идеальна.** Один раз повар **сам заходит в зал** — когда нужно вставить общий CSS на новую страницу. Почему так — в разделе «Кто вставляет CSS» ниже.

## Что делает каждый мир

### Service worker — «мозг»

**Что это:** фоновый JavaScript-файл. Запускается браузером **сам**, без открытия страницы. Живёт **пока есть события** — потом засыпает (об этом ниже).

**Что умеет:**
- Слушать события: новая страница открылась, пользователь переключил вкладку, пришло сообщение.
- Вставлять общий CSS во **все** вкладки через `chrome.scripting.insertCSS` — это API доступно **только** ему (см. «Кто вставляет CSS»).
- Читать и записывать **общие настройки расширения** — они хранятся отдельно от страниц и переживают перезапуск браузера.
- Управлять DNR-правилами — включать и выключать блокировку.
- Общаться с popup и content script через сообщения.
- **Один раз** прочитать карту domain-specific селекторов и **отдавать** её куски content script'ам по запросу.

**Что НЕ умеет:**
- **Читать содержимое вкладок напрямую** — не видеть DOM, не трогать элементы, не знать, что там написано. Только **через явные команды**: «вставь этот CSS во вкладку №5», «выполни этот код во вкладке №5».
- Жить **вечно**. Chrome **убивает** его через ~30 секунд без событий.

**Почему ему запрещено читать вкладки:** service worker работает **в фоне всё время**, видит **все** вкладки сразу. Если бы он мог читать их содержимое — вредоносное расширение **за один день** собрало бы данные всех сайтов, что ты открывал: пароли, карты, переписку. Chrome **не даёт** такой возможности.

**Наши файлы в `background/`** — это service worker и его модули.

### Content script — «руки»

**Что это:** JavaScript, который браузер **подсовывает в каждую страницу**, которую ты открываешь. «Content script» — это **роль кода**, а не имя одного файла: файлов у нас несколько, они вместе образуют один content script.

**Что умеет:**
- Видеть и менять DOM страницы — как обычный JS на сайте.
- Вставлять `<style>` с нашими CSS-правилами **напрямую в DOM** — это обычная DOM-операция, не требует chrome API.
- Нажимать кнопки (например, «Пропустить рекламу»).
- Следить за изменениями страницы через `MutationObserver`.
- Отправлять сообщения service worker'у (попросить селекторы, сообщить о чём-то).

**Что НЕ умеет:**
- Читать общие настройки расширения **напрямую** (только через service worker).
- Вставлять CSS в **другие** вкладки.
- Видеть переменные и замыкания сайта. Content script работает **в изолированном мире** — видит **только DOM**, но не внутренности JS сайта.

**Особенность:** content script **запускается заново** для каждой вкладки. Открыл 5 вкладок — 5 копий работают параллельно.

**Наши файлы в `content/`** — это content script и его модули.

### Popup — «лицо»

**Что это:** HTML-страница, которая открывается **по клику на иконку** расширения.

**Что умеет:**
- Показывать UI: переключатель «включено/выключено», список исключений, версию.
- Отправлять сообщения service worker'у (включить/выключить, добавить сайт в исключения).
- Читать состояние через service worker.

**Что НЕ умеет:**
- Жить долго. **Открыт — работает, закрыл — умер.** Никакой памяти между открытиями.
- Видеть DOM страницы сайта.

**Наши файлы в `popup/`** — это popup и его модули.

### Кто вставляет CSS — и почему «повар» лезет в зал

Тут нужна ясность, потому что в аналогии «service worker = повар, content script = официант» есть исключение.

Есть **два набора CSS**:

**Набор 1. Общий CSS** — файлы `content/cosmetic.css` и `content/cosmetic-manual.css`. Внутри селекторы, которые работают **на любом сайте**: `.ad-banner`, `ins.adsbygoogle`, `[data-role^="fox-tail"]`. Их ~14 000. Их называют **generic** — «общие», «родовые», универсальные.

**Набор 2. Domain-specific селекторы** — данные из `rules/cosmetic-map.json`. Для **каждого домена** — свой список селекторов. Например, для `rbc.ru` — одни, для `dzen.ru` — другие. Всего ~31 000 селекторов на 12 832 домена. Их называют **domain-specific** — «специфичные для домена». Английский термин оставляем, потому что так же пишут в uBlock и EasyList, и перевод только запутает.

**Почему нельзя положить всё в один файл:**
- Селекторы привязаны к домену. `.some-rbc-banner` имеет смысл **только** на `rbc.ru`. На `habr.com` он бесполезен — браузер всё равно спарсит правило, потратит память.
- 31 000 правил в одном CSS — это несколько мегабайт. Браузер будет тормозить на каждой странице.

**Как распределяются роли:**

**Общий CSS вставляет service worker** через `chrome.scripting.insertCSS`. Почему именно он: **этот API недоступен content script'у**. Chrome даёт `chrome.scripting` только фоновым контекстам — тем, кто «управляет» всеми вкладками. Content script привязан к **одной** странице и таких прав не имеет (иначе он мог бы вставлять стили в **другие** вкладки — дыра в безопасности). Значит, **вставлять общий CSS может только service worker** — «повар сам заносит тарелки в зал».

**Domain-specific селекторы вставляет content script сам**. Он не использует chrome API — он просто создаёт тег `<style>` через обычный `document.createElement` и кладёт туда **только те селекторы**, что нужны для текущего домена. Их ~10-50, не 31 000. Service worker при этом работает как **библиотекарь**: держит карту в памяти и выдаёт нужный кусок по запросу.

**Итого:**
- Общий CSS (~14 000 правил, один файл) → **service worker** через `insertCSS`.
- Domain-specific CSS (~10-50 правил на страницу, из карты) → **content script** через обычный `<style>` в DOM.

## Как миры общаются

Все три мира — **изолированы**. Они не видят переменные друг друга. Но они могут **отправлять сообщения** через Chrome API.

**Три функции, которые нужны знать:**

**1. `chrome.runtime.sendMessage(message)`** — отправить сообщение **кому-то в расширении**.

Кто именно получит — тот, кто **слушает** `chrome.runtime.onMessage`. Обычно это service worker (**он всегда есть**). Но popup и content script **тоже** могут слушать.

**2. `chrome.tabs.sendMessage(tabId, message)`** — отправить сообщение **в конкретную вкладку**.

Используется, когда service worker хочет сказать **content script'у** во **вкладке №5**: «сделай что-то». **Без `tabId`** content script **не найдёшь** — их много.

**3. `chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {...})`** — слушать сообщения.

Вызывается **каждый раз**, когда кто-то отправил сообщение. Внутри — обрабатываем и **отвечаем** через `sendResponse(result)`.

### Как выглядит обмен сообщениями в коде

**Popup отправляет → service worker получает:**

```js
// popup/popup.js — отправка
const response = await chrome.runtime.sendMessage({
  type: "popup→sw:getState",
  url: "https://rbc.ru/"
});

// background/lib/message-handler.js — получение (с асинхронным ответом)
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.type === "popup→sw:getState") {
    (async () => {
      const enabled = await getEnabled();          // ← await перед sendResponse
      sendResponse({ enabled });                    // ← отвечаем ПОСЛЕ await
    })();
    return true; // ← обязательно, потому что ответ асинхронный
  }
});
```

### Что такое `return true` — пошагово

Разберём этот `return true` — он выглядит странно, но объясняется просто.

**Сцена:**
1. Popup **отправил** сообщение service worker'у: «дай состояние».
2. Chrome **вызвал** функцию-обработчик в service worker'е.
3. Внутри обработчика мы **хотим** ответить — **но не сразу**: сначала сходить в хранилище, собрать данные, потом ответить. Это занимает **доли секунды**.
4. Вопрос: **пока мы «ходим» — Chrome ждёт? Или уже всё бросил?**

**Правило:** по умолчанию Chrome **не ждёт**. Как только функция-обработчик **вернула управление** — Chrome считает разговор законченным и **закрывает канал связи**. Если мы **позже** попытаемся ответить через `sendResponse` — ответ **не долетит**, канал закрыт.

**Что делает `return true`:** это **сигнал Chrome'у** — «я ещё тебе отвечу, подожди». Chrome **не закрывает канал**, ждёт `sendResponse`.

**Три варианта возврата из обработчика:**

- **`return;`** (или `undefined`) — «я уже всё сделал, отвечать больше не буду». Chrome **закрывает канал сразу**. Если позже вызовешь `sendResponse` — **не долетит**.
- **`return true;`** — «я ещё в работе, отвечу позже через `sendResponse`». Chrome **ждёт**.
- **`return false;`** — то же, что `return;`.

**Почему это контринтуитивно:** обычно `return true` в JS значит «успех, я закончил». Здесь — **наоборот**: «я ещё не закончил». Это **не наша прихоть**, а **требование Chrome API**. Возвращаемое значение функции здесь — не «результат работы», а **ответ на вопрос** Chrome: «Ты будешь отвечать позже, или канал можно закрывать?»

**Правило:** если внутри обработчика есть `await` **перед** `sendResponse` — **обязательно** `return true`.

**Правильно:**
```js
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.type === "popup→sw:getState") {
    (async () => {
      const enabled = await getEnabled();
      sendResponse({ enabled });
    })();
    return true; // ← «подожди, я отвечу»
  }
});
```

**Неправильно (ответ потеряется):**
```js
chrome.runtime.onMessage.addListener((msg, sender, sendResponse) => {
  if (msg.type === "popup→sw:getState") {
    (async () => {
      const enabled = await getEnabled();
      sendResponse({ enabled });
    })();
    // ← нет return true — Chrome закроет канал до sendResponse
  }
});
```

## Полный цикл — от запуска браузера до блокировки рекламы

Давай пройдём **весь путь**. Что происходит, когда ты запускаешь Chrome с нашим расширением и открываешь `rbc.ru`. По ходу будут термины, которые мы ещё не объясняли — не переживай, дальше разберём каждый.

### Фаза 1. Запуск браузера

1. Chrome читает `manifest.json` — паспорт расширения.
2. Находит там указание: «фон — это `background/service_worker.js`». Запускает его.
3. Service worker **регистрирует слушателей** — «подписки» на события браузера. Теперь он узнает:
   - когда пользователь открывает новую страницу,
   - когда переключает вкладки,
   - когда popup отправляет ему сообщение.
4. Service worker читает **настройки расширения** — включено ли расширение, какие сайты в списке исключений.
5. Применяет эти настройки к DNR-правилам — включает или выключает блокировку.

После этого service worker может **заснуть** — он больше не нужен, пока не произойдёт какое-то событие.

### Фаза 2. Ты открываешь `rbc.ru`

1. Браузер **будит** service worker: «эй, пользователь открыл новую страницу».
2. Service worker срабатывает на это событие и делает две вещи:
   - **Проверяет**, не выключено ли расширение и не в списке ли исключений `rbc.ru`. Если что-то из этого — ничего не делает.
   - Если всё ок — **вставляет общий CSS** (`cosmetic.css` + `cosmetic-manual.css`) **во все фреймы вкладки** через `chrome.scripting.insertCSS`. Это единственный способ вставить стили «снаружи» — content script такого права не имеет.
3. Chrome **подгружает content scripts** — код, который будет работать **внутри** этой вкладки.

### Фаза 3. Content script просит domain-specific селекторы

1. Content script запускается внутри `rbc.ru`.
2. Он **не знает**, какие селекторы нужны именно для `rbc.ru`. Общий CSS уже есть — но там только универсальные правила.
3. Content script **отправляет сообщение** service worker'у: «пришли мне domain-specific селекторы для `rbc.ru`».
4. Service worker **загружает карту** `cosmetic-map.json` в память (один раз — при первом запросе). В карте записи вида «для домена X — вот такие селекторы».
5. Service worker **выбирает** только нужные для `rbc.ru` — например, 42 селектора.
6. Отвечает content script'у.
7. Content script **сам вставляет** `<style>` в `<head>` страницы с этими 42 селекторами. Это **обычная DOM-операция**, не требует chrome API.
8. Реклама на `rbc.ru`, которую ловят эти 42 селектора, **исчезает**.

### Фаза 4. Сайт пытается загрузить рекламу через сеть

Параллельно Chrome сам применяет **DNR-правила** из `rules/ads.json`. Наш код тут **не участвует** — правила **уже в браузере**, Chrome применяет их **автоматически** при каждом запросе.

1. Сайт пытается загрузить скрипт с `https://ads.rbc.ru/banner.js`.
2. Chrome сверяет адрес с DNR-правилами.
3. Находит подходящее правило → **блокирует запрос**.
4. Скрипт рекламы не загружается.

### Фаза 5. Ты кликаешь на иконку расширения

1. Chrome **открывает popup** — маленькое окно.
2. Popup спрашивает у service worker'а: «какое сейчас состояние?»
3. Service worker отвечает: «включено, список исключений пустой, ты на `rbc.ru`».
4. Popup показывает переключатель (включён), пустой список исключений, кнопку «+ Добавить `rbc.ru`».
5. Ты кликаешь «Добавить» → popup просит service worker'а добавить сайт в исключения → service worker обновляет настройки → DNR-правило «не блокировать `rbc.ru`» создаётся → реклама на `rbc.ru` **перестаёт блокироваться** (но только на нём, на остальных сайтах — работает как раньше).

## Почему такая архитектура

Может возникнуть вопрос: почему так сложно? Почему нельзя **один** файл, который **всё** делает?

Потому что **Chrome не даёт** так. Три мира — **обязательная** часть MV3:
- Service worker **не читает** содержимое вкладок — только через явные команды. Это защита от скрытого чтения всех твоих сайтов одним фоновым скриптом.
- Content script **не может** жить вечно — он **привязан к вкладке**.
- Popup **не может** работать в фоне — он **только** когда открыт.

Мы **вынуждены** жить в этих рамках. Взамен получаем:
- **Безопасность** — расширение **не может** прочитать всё, что ты видишь.
- **Экономию** — service worker спит, память не тратится.
- **Изоляцию** — content script **не мешает** коду сайта.


**Про «что попадает в расширение при публикации».**

При **разработке** ты грузишь расширение через `Load unpacked` — Chrome читает `manifest.json` и **берёт только те файлы, что там указаны**. Остальное (`docs/`, `lists/`, `tools/`, `node_modules/`) **лежит рядом**, но Chrome **их не трогает**. Они как бы невидимы.

При **публикации** в Chrome Web Store нужно **собрать ZIP** — и вот тут **ты сам** решаешь, что туда класть. По-хорошему в ZIP идёт **только то, что нужно Chrome**:
- `manifest.json`
- `background/`, `content/`, `popup/`, `shared/`, `rules/`

**Что НЕ нужно в ZIP:**
- `docs/` — документация для тебя.
- `lists/` — исходные списки для конвертера.
- `tools/` — сам конвертер.
- `package.json`, `node_modules/` — для npm.

Про сборку ZIP поговорим в главе 11.

## Что дальше

В следующей главе — построчный разбор `manifest.json`. Что там за каждое поле, почему именно эти права, зачем `host_permissions`, почему `type: "module"` только у service worker, но не у content scripts.
